# ЧАСТЬ I. ДЕЙСТВИЯ И ПРИОРИТЕТЫ

## 1. Где мы сейчас

**Этап 0 (валидация ядра) — идёт.** Сквозной конвейер работает на реальных данных с обоими
ключами (Anthropic + Тендерплан): id/файл ТЗ → парсинг → извлечение (Claude) → семантика →

   `источник_света=«Ксенон-галогенная лампа»` vs карточка `LED` — реальное critical-нарушение.
   Гипотеза: реальное ТЗ (по эксперту) даёт «Соответствие/Наличие», а не жёсткий ксенон → это
   ФИДЕЛЬНОСТЬ ИЗВЛЕЧЕНИЯ, новый хвост. Полный флип trap→eligible подтвердить ЖИВЫМ прогоном
   `check_tender --id 6a6034cc` с ключом. Ядро `matcher.py` тронуто осторожно (инвариант). Golden-кейс:
   `data/golden/ophthalmoscope_6a6034cc.json` (expected eligible, engine disqualified — регресс-ловушка).

## 5. Ключевые решения (зафиксировано)

- **Ключ Anthropic — только для беспилота.** Нужен, чтобы `extractor.py` крутился в cron
  без человека. Этап 0 при этом НЕ заблокирован: извлекает Claude Code на подписке.
  `export ANTHROPIC_API_KEY=...` (в git не коммитить). Маршрутизация уже заложена (`models.py`).
- **Источник данных для MVP — API Тендерплана** (оплаченный тариф, PAT) как временный
  **заменяемый** источник: быстрый старт без интеграции ЕИС. За интерфейсом `source.py`.
  Тендерплан — конкурент (§7), поэтому осознанно временно; официальная интеграция ЕИС —
  цель прода (второй адаптер), чтобы уйти от вендор-локина. Дифференциатор (извлечение+
  матчинг) от источника не зависит.
- **Мультиарендность — базовое требование** с первого дня (регистрация, компании, изоляция
  товаров по `company_id`). Заложена в модель данных (§11.0).
- **Услуги / работы / НИОКР — ВНЕ продукта.** Требования там прозой, «матчинг по спекам»
  неприменим — это другой продукт. Делаем только поставку товара (Tier A сейчас, Tier B потом).
- **Безопасность by design — с первого дня, не «прикрутим потом».** Аккаунт поставщика = доступ к
  его тендерной аналитике (коммерческая тайна), поэтому аутентификацию проектируем защищённой
  сразу: хеш паролей (argon2/bcrypt, не MD5/SHA), HTTPS-only, серверная валидация всего ввода,
  никакой утечки «существует ли юзер» в ошибках логина. Защита от brute-force — **rate limiting**
  (экспоненциальная задержка + лимит на IP) и **временная** блокировка (~15 мин), НЕ вечный
  lockout после N попыток (иначе злоумышленник блокирует чужие аккаунты — DoS). Главный барьер —
  **2FA / подтверждение входа через Telegram-бота** (второй фактор сильнее любого лимита попыток).
  Секреты (`ANTHROPIC_API_KEY`, `TENDERPLAN_TOKEN`, ключ заказчика) — только в окружении, не в
  коде/git/чате; заказчику — отдельный ключ с лимитом трат в консоли Anthropic.

## 6. Открытые технические долги (в Этап 1, не блокируют Этап 0)

- **Версионность закупки.** Заказчик может выпустить изменения к ТЗ после публикации →
  перепрогонять матчинг и уведомлять «ТЗ изменилось, вердикт мог смениться».
- **Отказоустойчивость извлечения.** Если LLM вернул невалидный JSON или частично вытащил
  таблицу — нужен retry с уточняющим промптом + порог «мало требований → эскалация на Opus».
- **КТРУ-recall на закупках-НАБОРАХ (вскрыто 2026-07-22, тендер 67e1270f).** Заказчик кодирует
  диагностический набор (оториноофтальмоскоп: отоскоп+офтальмоскоп) под ШИРОКИМ/чужим КТРУ
  (`32.50.13` «ОТОСКОПЫ»), а не под КТРУ офтальмоскопа `26.60.12` → `ktru_relation`=`none` →
  движок ложно отсекает релевантную закупку. Нужно: смягчить сверку для родительских кодов
  (префикс-совпадение по классу) ИЛИ keyword-fallback, когда товар — компонент набора. Плюс сам
  матчинг «single-product ↔ ТЗ набора» — товар покрывает лишь часть набора (аналог многолота).
- **Источник требований: характеристики ПОЗИЦИИ, а не общий ТЗ-докс (вскрыто 2026-07-23, халаты 69e0ac8e).**
  Экстрактор из полного 44-ФЗ ТЗ-докса гребёт КОНТРАКТНУЮ ОБВЯЗКУ (сертификат/декларация соответствия,
  разрешение к применению, протокол испытаний, пожарная безопасность, маркировка на русском, гарантия)
  как «требования к товару» → лишние пробелы, заниженный %. На халате: против ТЗ-докса 48%, против
  ХАРАКТЕРИСТИК ПОЗИЦИИ (структурные, из карточки ЕИС/КТРУ) — 100% (7/7, реальные хар-ки товара).
  Вывод: приоритетный источник требований — характеристики позиции (см. §3.3 «2-й источник — КТРУ-базис»),
  а из ТЗ-докса брать только товарные хар-ки, не контрактную обвязку. Нужен парсер характеристик позиции
  (Тендерплан/ЕИС) ИЛИ фильтр «контрактные документарные термины» в экстракторе.
- **CA-бандл `zakupki.mos.ru` (московский ЕИС).** Вложения качаются с `zakupki.mos.ru`, чей CA
  не в бандле (certifi + Минцифры для zakupki.gov.ru) → `CERTIFICATE_VERIFY_FAILED`. Добавить CA
  московского портала в `setup_ca_bundle.py`.

# ЧАСТЬ II. СПРАВКА (как устроено)

## 7. Идея и отличие от конкурентов

Поставщик заводит свою номенклатуру с техническими характеристиками. Система сама находит
закупки, читает **текст ТЗ каждой** и выдаёт вердикт: **проходит / не проходит / нужно
подтвердить**, с процентом соответствия и разбором по каждому требованию.

**Отличие от конкурентов (Seldon, Тендерплан, Контур):** они матчат по классификаторам
(ОКПД2 / КТРУ) и ключевым словам. Мы матчим по **фактическим характеристикам из ТЗ** —
толщина ≥0,11 мм, размеры S/M/L, тип отделки, — которых в классификаторах нет. Именно там
заказчики по ст. 33 44-ФЗ пишут требования руками, и классификаторный поиск слеп.

## 8. Сквозной принцип архитектуры

> **Можно сделать кодом — делай кодом. LLM — только там, где нужен «разум».**

LLM НЕ читает каждую закупку целиком. Дорогой «разум» подключается хирургически и только к
финалистам. Основную воронку прожимает дешёвый детерминированный код + эмбеддинги. Это
держит себестоимость на копейках при любом масштабе. Воронка сужается на каждом шаге:

```
Все закупки (сотни тыс./день)
   │  [код: фильтр по ОКПД2/КТРУ/ключевым словам]
   ▼
Грубые кандидаты (сотни/день на поставщика)
   │  [эмбеддинги: семантический отсев]
   ▼
Кандидаты на глубокий разбор (десятки/день)
   │  [код: скачать вложения ТЗ]
   ▼
ТЗ извлечены в текст (+ OCR сканов)
   │  [LLM: вытащить структурированные требования]
   ▼
Требования в JSON
   │  [код + LLM: матчинг с карточкой товара]
   ▼
Вердикт: % соответствия + статусы по каждому требованию
   │  [LLM: человекочитаемое объяснение]
   ▼
Уведомление поставщику
```

## 9. Конвейер по шагам: кто, что, чем

### Шаг 0. Онбординг поставщика (разово)

- **Что:** поставщик заводит карточки товаров с характеристиками (форма или импорт из Excel/1С).
- **Кто:** фронтенд + код. LLM-помощник **опционально** нормализует «грязный» прайс в структуру.
- **LLM:** Haiku 4.5 — разбор прайса в JSON (разово, дёшево). **Выход:** карточки товаров (§11.1).

### Шаг 1. Сбор закупок (discovery)

- **Что:** непрерывно тянем новые/изменённые закупки. **Источники:** ЕИС / ЭТП (сейчас Тендерплан).
- **Кто:** **код** (планировщик + загрузчик), инкрементально по дате публикации. **LLM:** нет.
- **Выход:** сырые карточки закупок (реестр, ОКПД2/КТРУ, НМЦК, заказчик, ссылки на вложения).

### Шаг 2. Грубые фильтры воронки (дёшево → дорого) ← дешёвый код, отсекает 99%

- **Что:** оставить только релевантные и **актуальные** закупки до дорогого анализа ТЗ.
- **Кто:** **код** (`filter.py`), по порядку:
  1. **КТРУ / ОКПД2** (обязательное поле поставщика; список кодов, матч по префиксу);
  2. **Срок подачи** — окно дней до дедлайна (напр. 1–29): только активные, где успеваешь подать;
  3. **Регион** — вся РФ или выбранные коды регионов (где поставщик возит).
- **LLM (опционально):** Haiku 4.5 — расширение запроса синонимами, редко (при настройке профиля).
- **Сборные лоты:** многопозиционный тендер (товар — 1 из N позиций) КТРУ-фильтр проходит и **не
  отсекается**; переключатель `lot_mode` (solo / any) — см. §11.4. Матчинг — по конкретной позиции.
- **Выход:** короткий пул кандидатов → в глубокий анализ (шаги 4–8).

### Шаг 3. Семантический отсев (coarse matching)

- **Что:** отсеять явно нерелевантное до дорогого разбора («перчатки боксёрские» ≠ «медицинские»).
- **Кто:** **эмбеддинги** (векторное сходство «предмет закупки» ↔ «товар»), быстро и почти бесплатно.
- **Модель:** мультиязычный эмбеддер под русский (bge-m3 / multilingual-e5) + pgvector.

### Шаг 4. Забор ТЗ (fetch)

- **Что:** скачать вложения (описание объекта, проект контракта): .docx / .pdf / .xls / сканы.
- **Кто:** **код** (загрузчик из ЕИС/ЭТП). **LLM:** нет. **Выход:** файлы ТЗ по каждому кандидату.

### Шаг 5. Извлечение текста ТЗ (parse + OCR)

- **Что:** документ → чистый текст/таблицы.
- **Кто:** .docx/.xlsx/текстовый .pdf → **код** (python-docx, openpyxl, pdfplumber); скан → **OCR**.
- **OCR:** Tesseract (rus) на старте; кривые сканы — vision-модель Claude как fallback.

### Шаг 6. Извлечение требований (structured extraction) ← сердце №1

- **Что:** из текста ТЗ — список требований в строгий JSON: характеристика, оператор
  (=, ≥, ≤, диапазон, «одно из»), значение, единица, жёсткость («не изменяется»=дисквалификатор /
  «участник указывает»=мягкое), документарные требования (РУ, срок годности).
- **Кто:** **LLM** со строгой JSON-схемой. **Модель:** **Sonnet 5** (Haiku — простые, Opus 4.8 — эскалация).

### Шаг 7. Матчинг товар ↔ требования ← сердце №2

- **Что:** сверить каждое требование с карточкой, присвоить статус.
- **Кто:** гибрид: **код** — числа и логика операторов (0,11 ≥ 0,11, наборы, пороги, дисквалификаторы);
  **LLM** — только семантическая эквивалентность формулировок, точечно.
- **Выход:** по требованию статус ✅ проходит / ❌ нарушение / ⚠️ пробел.

### Шаг 8. Вердикт и скоринг

- **Кто:** **код** — расчёт % и статуса по правилам (§12); **LLM** — текст объяснения поставщику.
- **Модель:** Opus 4.8 (понятный русский вердикт). **Выход:** карточка результата (§11.3).

### Шаг 9. Доставка и лента результатов

- **Что:** лента в кабинете + алерты (Telegram / e-mail). **Кто:** **код**. **LLM:** нет.
- **Сортировка ленты (решено):** по **% совпадения по убыванию** (100% сверху → вниз).
  Сверху — где проходишь целиком, ниже — с пробелами (`eligible_with_gaps`).
- **Дисквалифицированные** (`disqualified`, нарушено обязательное требование) — **не в основной
  ленте**, а отдельной свёрнутой секцией «не подходит».
- **Вторичная сортировка при равном %:** по сроку подачи (срочные выше) — не упустить закрывающиеся.
- Каждая строка ленты = вердикт (% + разбор) + карточка контракта (§4 Этап 1) + пометка
  «позиция N из M» для сборных лотов (§11.4).

## 11. Модели данных

> **Мультиарендность заложена с первого дня.** Иерархия: `Company` (арендатор) → `User`
> (роли) → `Product[]` → `MatchResult[]`. Закупки (`Purchase`) и требования — **общие** для
> всех арендаторов (публичные данные ЕИС); товары и результаты изолированы по `company_id`.

### 11.0. Компания и пользователь (`Company`, `User`)

```json
{ "id": "co_acme", "name": "ООО «Медснаб»", "inn": "7701234567",
  "plan": "pilot", "created_at": "2026-07-20" }

{ "id": "usr_01", "company_id": "co_acme", "email": "buyer@medsnab.ru",
  "role": "owner", "created_at": "2026-07-20" }
```

Изоляция: каждая строка `Product`/`MatchResult`/профиля несёт `company_id`; любой запрос к
товарным данным фильтруется по `company_id` (row-level, не только UI). Регистрация: завёл
компанию (`owner`) либо приглашён (`member`).

### 11.1. Карточка товара (`Product`)

```json
{
  "id": "gloves-nitrile-blue",
  "company_id": "co_acme",
  "name": "Перчатки смотровые нитриловые, неопудренные, нестерильные",
  "attributes": [
    {"key": "материал", "value": "нитрил", "critical": true},
    {"key": "стерильность", "value": "нет"},
    {"key": "опудренность", "value": "нет"},
    {"key": "размеры", "value": ["XS","S","M","L"], "status": "declared"},
    {"key": "толщина_пальцы_мм", "value": 0.11, "status": "confirmable", "doc": "протокол испытаний"}
  ],
  "documents": ["регистрационное_удостоверение"]
}
```

Три статуса данных: `declared` (в карточке), `confirmable` (подтверждается документом), `gap` (нет).

### 11.2. Требование закупки (`Requirement`)

```json
{
  "key": "толщина_пальцы_мм",
  "raw": "Одинарная толщина (в области пальцев) ≥ 0,11 мм",
  "operator": "gte",        // eq | gte | lte | range | one_of | set | present
  "value": 0.11, "unit": "мм",
  "hardness": "soft",       // hard = дисквалификатор | soft = участник указывает
  "type": "technical"        // technical | documentary
}
```

### 11.3. Результат сопоставления (`MatchResult`)

```json
{
  "purchase_id": "...", "company_id": "co_acme", "product_id": "gloves-nitrile-blue",
  "score": 92, "verdict": "eligible_with_gaps",   // eligible | eligible_with_gaps | disqualified
  "checks": [
    {"req": "материал=нитрил", "status": "pass"},
    {"req": "размеры S,M,L", "status": "gap", "action": "подтвердить наличие S/M/L"}
  ],
  "explanation": "Проходишь по всем техническим характеристикам. Закрой пробел: размеры."
}
```

### 11.4. Карточка поставщика: онбординг, настройки поиска, сборные лоты

**Иерархия:** `Company` → `Product[]` (+ настройки поиска). Каждый товар матчится независимо,
лента результатов агрегирует по компании.

**Поля карточки товара:**

| Поле               | Что                                                                                             | Роль                                                           |
| ---------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `name`               | название товара                                                                      | отображение                                             |
| **`ktru[]`**   | **обязательно** — коды КТРУ/ОКПД2 (список)                     | якорь воронки (шаг 2)                               |
| `category`           | выводится из КТРУ → профиль категории                              | связь со справочником                           |
| `attributes[]`       | характеристики`{key, value, status, doc}`                                          | сердце матчинга (§11.1)                             |
| `documents[]`        | какие документы поставщик даёт (РУ №, серт., протоколы) | закрывают документарные требования |
| `delivery_regions[]` | коды регионов поставки                                                         | фильтр воронки (шаг 2)                             |
| `search{}`           | настройки поиска (ниже)                                                         | параметры воронки                                  |

**Онбординг — заводить карточку можно И руками, И автоматически (оба способа в MVP):**
(1) **форма по категории** — поля подсказывает профиль КТРУ (поставщик заполняет вручную);
(2) **загрузка спеки/ТЗ товара** (docx/pdf/фото) → LLM извлекает характеристики (тот же extractor,
развёрнутый на товар) → поставщик проверяет/правит форму. Плюс импорт Excel/1С (Haiku нормализует).
Если поставщик не знает КТРУ — LLM подсказывает по названию.

**Настройки поиска (`search`) — на КАЖДЫЙ товар отдельно** (решено): регионы поставки, окно срока
подачи (дней), min/max НМЦК, **режим лота** `lot_mode`. Каждый товар ищется по своим настройкам.

**Сборные лоты (важно — не терять):** тендер бывает многопозиционным (напр. 5 позиций, товар —
одна из них). В РФ лот — «всё или ничего». Переключатель `search.lot_mode`:

- `solo` — только чистые лоты (товар = вся/основная позиция, подаёшься напрямую);
- **`any` (дефолт)** — включая сборные, **не отсекаем**, с пометкой «позиция N из M» + что ещё в лоте.

Движок: многопозиционный тендер проходит КТРУ-фильтр (совпал по одной позиции — не выкидываем);
**матчинг идёт по конкретной позиции** (её КТРУ = товар), не по всему лоту. В карточке результата —
«твой товар = позиция N из M, остальное в лоте: …». Данные по позициям уже есть в источнике
(Тендерплан `fullinfo`, таблица `ObjectInfo.Objects`: Name/КТРУ/Quantity/Price на позицию).

**Ключевой инсайт:** карточка товара и требование закупки — одна структура `{key, operator, value}`;
матчинг сводит их. Профиль категории (от КТРУ) задаёт словарь ключей и синонимов
(ISO 7376 ⇔ Flexline, полиамид ⇔ пластик) — товар это конкретика, профиль общий справочник.

## 12. Логика скоринга

1. **Дисквалификаторы (hard).** Нарушено `hard`-требование → `disqualified`, процент не важен.
2. **Пробелы (gap).** Требование есть, данных в карточке нет → не «−балл», а флаг «подтвердить».
   Это ценность продукта, а не ошибка.
3. **Процент** = взвешенная доля выполненных требований (`technical` весит больше `documentary`).
4. **Статусы:** `eligible` (всё pass) · `eligible_with_gaps` (нет нарушений, есть пробелы) ·
   `disqualified` (нарушение hard).

## 14. Генерализация: профили категорий

**Движок не привязан к перчаткам.** Ядро (извлечение → матчинг → скоринг) category-agnostic:
карточка и требование — произвольные `{key, operator, value, unit}`, логика работает на
операторах (`≥ ≤ = one_of set semantic`), которым всё равно, `0,11 ≥ 0,11` это или `5,5 кВт ≥ 4`.
Переход на другой товар **не требует нового кода** — меняется только профиль.

**Профиль категории (данные, не код):** коды ОКПД2/КТРУ, ключевые слова/синонимы, словарь
характеристик, единицы, критические характеристики (дисквалификаторы), обязательные документы.

**Онбординг новой категории:** взять 5–10 реальных ТЗ → Opus 4.8 предлагает черновик профиля →
эксперт валидирует (~30–60 мин) → прогон 20–30 ТЗ на точность → в прод. **~1–2 дня, не месяцы.**

**Уровни сложности:**

| Уровень                                                | Категории                                                                                               | Статус              |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 🟢**Tier A** — товары со spec-таблицей | перчатки, расходники, канцелярия, стройматериалы, реагенты     | **в работе** |
| 🟡 Tier B — оборудование, медтехника   | десятки характеристик, ссылки на ГОСТ, больше эскалаций на Opus | задел                |

Услуги/работы/НИОКР — вне продукта (см. §5).

## 15. Экономика (ориентир)

**Себестоимость на закупку-финалист:** эмбеддинги/фильтр ~0 ₽; извлечение (Sonnet 5) + OCR +
вердикт — единицы рублей каждое. Десятки финалистов/день ⇒ **десятки–сотни ₽/день на поставщика**.

**Монетизация:** дорогая B2B-подписка (тендеры = прямые деньги поставщика). Ориентир —
15–50 тыс. ₽/мес в зависимости от числа категорий/товаров. Маржа высокая: costs на порядок ниже чека.

| Риск                                                                                                   | Митигейт                                                                                                                                                                                       |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
